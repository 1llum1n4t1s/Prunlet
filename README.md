# Prunlet — Anti “blocked by policy”

Prunlet is a tool for Windows, Apple Silicon Mac and Linux that routes AI agents' file and folder deletion through a dedicated CLI and MCP server, so that cleanup stops less often on `blocked by policy`. It standardizes on handing permitted deletions to Prunlet from the start.

Files and folders normally go to the OS trash. Prunlet stores no file operation records, operation IDs or restore snapshots; restoring from and retaining the trash is left to the OS. It does not ship with any particular AI tool and is installed as a standalone app. You can optionally register its MCP server, CLI and hook with each AI tool; the hook inspects and denies direct deletions and points to the CLI procedure. Published by Kagayoi.

It handles files and empty folders, and deletes a whole folder when `--recursive` is given explicitly. Link targets are never followed. A hard link moved to the trash still shares its content with the surviving aliases. Conditional permanent deletion and [registry deletion and restoration](#registry-deletion-and-restoration) are Windows-only.

## Using it against `blocked by policy`

Where cleanup tends to stop on deletion commands generated by AI, such as `Remove-Item` or `rm`, hand permitted deletions to the Prunlet CLI from the start. Codex on Apple Silicon Mac and Linux uses the CLI and configuration placed during installation. [macOS installation](docs/macos.md) · [Linux installation](docs/linux.md)

On Windows, use it in this order:

1. Install Prunlet as a standalone app with the command in [Installation and updates](#installation-and-updates) below. It does not touch the configuration files of AI tools.
2. Register the startup command from [Registering with an MCP host](#registering-with-an-mcp-host) with the AI tools (MCP hosts) you use. To call the CLI directly, write the absolute paths of the installed CLI and configuration into the AI tool's instructions. To register everything with Codex at once, use [Registering with Codex (optional)](#registering-with-codex-optional).
3. Ask for work and cleanup as usual. The CLI is called directly from CMD (`shell: cmd.exe`, `login: false`) with the absolute paths of the installed CLI and configuration. You do not need to add the same instructions to each repository.

To ask for cleanup explicitly, say something like:

> Clean up the unneeded temporary files and work folders created this time with the Prunlet CLI from the start.

Pass paths with spaces, Unicode, long paths or multiple targets as a UTF-8 JSON list with `--paths-file`, and give `--recursive` explicitly for non-empty folders. See [Deletion and restoration](#deletion-and-restoration) for the actual commands and how to restore.

The hook is an aid that detects and denies direct deletions and points to the CLI procedure; it does not convert commands automatically. To avoid repeated failures and retries, the baseline is to use the CLI from the first attempt through the shared instructions. Host and OS permissions, approvals and management policies still apply. If a call to Prunlet itself is denied, stop and do not retry another way. See the [integration guide](docs/integration.md) for registration and inspection scope.

PowerShell scripts that Codex sends to a Mac or elsewhere must be passed in the explicit child-PowerShell form described in the [hook integration guide](docs/integration.md#hookの検査範囲). Codex's hook input does not include the executing shell, so specifying only `shell: "pwsh"` cannot distinguish deletions inside a here-string.

## Installation and updates

Versions released before distribution moved to the signed manifests on `https://prunlet.kagayoi.com` (the versions distributed through GitHub Releases) cannot detect newer releases. They keep running the current version without breaking, but they do not migrate automatically, so reinstall once: on Windows, run the installer command in [Windows](#windows) again; on Apple Silicon Mac and Linux, follow [reinstalling on macOS](docs/macos.md#旧版からの再導入) or [reinstalling on Linux](docs/linux.md#旧版からの再導入).

### Apple Silicon Mac

`scripts/Install-Prunlet.sh` gets the signed release manifest from `https://prunlet.kagayoi.com`, verifies it with the public key built into the script, and downloads `prunlet-update-osx-arm64.zip` from the location recorded in it. It performs the download, size and SHA-256 checks, signature and notarization verification, and a fresh installation into a dedicated folder in one run (see [macOS installation](docs/macos.md)). Register the MCP server with Codex or other hosts yourself, using the configuration lines it prints. A registered MCP server checks for updates at startup and postpones them to a later start while in use.

### Linux

Get `prunlet-linux-x64.tar.gz` or `prunlet-linux-arm64.tar.gz` for your CPU from `https://prunlet.kagayoi.com`. Its location and SHA-256 are recorded in the signed release manifest; for a quick download, the fixed names and the `.sha256` files of the same name are also under `https://prunlet.kagayoi.com/download/latest/`.

See [Linux installation](docs/linux.md#初回インストール) for verifying the signed manifest and the checksum, placing it in a dedicated directory and registering it with Codex. When placed as described, the official build checks for updates when the MCP server starts and postpones them to a later start while in use.

### Windows

Windows x64 and ARM64 are supported. The installer below downloads the signed prebuilt package (`prunlet-update-<runtime>.zip`) of the latest release from `https://prunlet.kagayoi.com` and places it. Only PowerShell 7 is required; Rust, the MSVC build tools and the Windows SDK are not needed.

| Target | Installer option |
| --- | --- |
| Windows x64 | `-Runtime win-x64` (default) |
| Windows ARM64 | `-Runtime win-arm64` |

On Windows ARM64, add `-Runtime` explicitly to the command below. To choose x64 emulation, specify `-Runtime win-x64`.

```powershell
$installerDirectory = Join-Path ([IO.Path]::GetTempPath()) ('Prunlet\bootstrap-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $installerDirectory | Out-Null
$installer = Join-Path $installerDirectory 'Install-Prunlet.ps1'
Invoke-WebRequest 'https://raw.githubusercontent.com/1llum1n4t1s/Prunlet/main/scripts/Install-Prunlet.ps1' -OutFile $installer
pwsh -NoProfile -File $installer
```

Installation and updates need no GitHub account, sign-in or token.

The installer gets the signed manifest of the latest release (`latest/<runtime>.json`) from `https://prunlet.kagayoi.com`, verifies its signature with the public key built into the installer, and checks that the product, repository, runtime, package name and download location match. It downloads the ZIP from that fixed location without following redirects and, before placing it, verifies the length and SHA-256 recorded in the manifest, the list of bundled files and each hash, the commit and runtime, and the Authenticode signature of the executables (Valid, with the expected signer and a timestamp). These are the same checks as the startup auto-update. If the manifest cannot be retrieved or any check fails, it stops without writing anything. It never builds from source or switches to a local clone.

The default installation directory is `%USERPROFILE%\.local\Prunlet`. It places `bin\prunlet.exe`, the registration scripts and the shared instructions, and records the source, branch, commit and package hash in `source-info.json` in the same format as the startup auto-update. By default it writes nothing to the configuration files or folders of Codex or other AI tools, and registers only the maintenance task and the update task.

The auto-update checks the signed manifest at `https://prunlet.kagayoi.com` when an MCP host starts the Prunlet MCP server and from the update task the installer registers (daily at 12:30 and 10 minutes after logon, without a window), and switches over once the old MCP server and maintenance processes have exited. Only a release newer than the installed version is applied. Because of the update task, PCs that do not register the MCP server also follow the latest release. The auto-update does not rebuild from source. Running the product executables does not require installing the .NET runtime or the VC runtime. While in use, nothing is terminated; it checks again at the next MCP start. If communication, download or verification fails, nothing is applied and it uses the current version as long as the pre-update state is safely preserved.

The auto-update trusts only the signature made with the dedicated release key. The release workflow signs the manifest only after checking that the commit is on `main` and building, signing and verifying the package. See the [startup auto-update design](DESIGN.md#起動時自動更新) for how verification works and what is trusted.

Update data is managed within a dedicated 2 GiB budget. Verified areas are reused, and unknown data and interrupted output are preserved. When space runs short, the update is postponed; registry recovery data is never cleaned up for it.

#### Registering with an MCP host

For MCP hosts such as Toolport or Claude Code, register the installed startup script as a stdio server. Specify PowerShell 7 as `pwsh` (for the Microsoft Store version, `%LOCALAPPDATA%\Microsoft\WindowsApps\pwsh.exe`), and do not use the absolute path of a PowerShell bundled with an AI tool.

```text
command: pwsh
args:    -NoProfile -NonInteractive -File %USERPROFILE%\.local\Prunlet\bin\start-prunlet-mcp.ps1 -ExecutablePath %USERPROFILE%\.local\Prunlet\bin\prunlet.exe -ConfigPath %USERPROFILE%\.local\Prunlet\config.json
```

Replace `%USERPROFILE%` with the actual absolute path. `-CodexHome` is not needed. Only when an earlier registration remains in Codex does the startup script check it, read-only, and protect it.

#### Registering with Codex (optional)

Only to register everything with Codex at once, add `-RegisterCodex -RegisterAgentInstructions` to the installer above. This registers Codex's MCP server, the hook for the native executable, and shared instructions that use the Prunlet CLI from the start, into CodexHome (`CODEX_HOME`, or `%USERPROFILE%\.codex` if unset).

After installing or updating with `-RegisterCodex`, open `/hooks` in Codex, review the Prunlet hook definition and trust it. The installer does not change trust settings; `requiresHookTrust` in its result tells you that this step is needed. Restart Codex and confirm that the MCP server, shared instructions and hook are loaded. See the [integration guide](docs/integration.md#登録) for registering and unregistering.

`-RegisterAgentInstructions` above is an explicit option that registers `PRUNLET.md` in the Codex home, together with a dedicated reference and the absolute paths of the installed executable and configuration in the shared `AGENTS.md`. Without adding anything to each repository, it instructs Codex to delete with the Prunlet CLI on CMD from the start. If the executable or configuration path itself cannot be expressed safely in CMD, choose the MCP server, which uses the same core, before running. Leave this option out if you do not want the shared instructions changed.

The auto-update switches only to candidates whose registrations, including the shared instructions, need no change. If the registered `PRUNLET.md` differs from the candidate only in CRLF versus LF line endings, the existing file is kept as is. If a registration would need to be overwritten, or a change to a registration by the user is detected, the update is held. When updating manually with the installer, specify the same `-RegisterAgentInstructions` if the shared instructions are registered. See [shared agent instructions](docs/integration.md#エージェント共通指示) for details.

For the first update from an old version without the auto-update, or for a manual update, download the latest installer again and run it. The existing `config.json` is kept, except for a one-time migration of the retention capacity. Old recovery data is handled by an [explicit migration](#migrating-old-file-recovery-data). Folders to delete do not need to be registered in advance. The old `-AllowedRoot` is accepted as a compatibility argument but does not restrict what can be deleted. Change the installation directory with `-InstallDirectory`. Your clone path is never registered in the AI tools' configuration.

If an existing managed installation is inside a Git repository and the update stops at the normal destination check, you can add `-UpdateManagedInstallation -InstallDirectory <absolute path of the existing installation>` to the re-downloaded installer. It checks that the existing configuration, installation information and product hashes match, and updates an installation that has no Git-tracked files and is either excluded by Git or matches the current shared CLI registration. An installation that cannot be verified is preserved and the installer stops. See the [integration guide](docs/integration.md#手動の設定準備) for the conditions.

To require a match with a release you checked beforehand, add `-ExpectedCommitSha <40-character SHA>`. If the commit of the latest release differs, it stops before installing.

The downloaded bootstrap files are temporary. After checking the installation result, clean up only that bootstrap directory. Do not include the app's installation directory or the recovery data in the cleanup.

If there are backups of the pre-update products or of the Codex configuration before registration, `updateBackupDirectory` in the installation result shows where they are. The default is `%LOCALAPPDATA%\Prunlet\Backups\install-<ID>`. After confirming the behavior and registrations and that no recovery is needed, clean up only the backup of that installation. See the [integration guide](docs/integration.md) for the configuration backups of the integration scripts.

In an MSIX environment where AppData is redirected to another location, you can set the parent of the update backups explicitly with `-UpdateBackupRoot <absolute path of the actual location>`. A per-installation `install-<ID>` is created under it. A per-installation destination that overlaps a repository, the Codex home, the installation directory, the work area or the recovery data is refused. If an old PowerShell hook remains, the installer moves it to the Windows Recycle Bin with Prunlet and saves the result in `retired-products.json` in the same update backup.

## Initial configuration

On macOS and Linux, the configuration is created by each OS's installation procedure. The following is the initial configuration for Windows. If you used the Windows installer, it is already initialized. Manually, specify where to store registry recovery data. `init` does not overwrite an existing configuration.

```powershell
$config = Join-Path $env:USERPROFILE '.local\Prunlet\config.json'
$backup = Join-Path $env:USERPROFILE '.local\Prunlet\recovery'
New-Item -ItemType Directory -Path (Split-Path $config), $backup -Force | Out-Null
$exe = Join-Path $env:USERPROFILE '.local\Prunlet\bin\prunlet.exe'
& $exe --config $config init --backup-directory $backup
& $exe --config $config migrate --dry-run
& $exe --config $config migrate --apply
```

`backupDirectory` is a protected area for registry snapshots and old data from before the migration. It stores no records or content of new file deletions. Registry records are stored under the dedicated `.registry-records-v1`. The configuration's `allowedRoots` and the old `--allowed-root` are compatibility inputs and are not used as an allowlist of what can be deleted.

A manual `init` only creates the configuration. Before using the registry, check the targets with `migrate --dry-run` and run `migrate --apply`. If not migrated, normal registry operations stop with `migration_required` and do not search the old file area automatically. File deletion does not depend on the registry migration status.

```json
{
  "schema": 1,
  "backupDirectory": "C:\\Users\\you\\.local\\Prunlet\\recovery",
  "retentionDays": 7,
  "maxRecoveryBytes": 1073741824
}
```

## Deletion and restoration

### On Apple Silicon Mac

Use the absolute paths of the executable and configuration shown in the [macOS CLI example](docs/macos.md). Check the targets with `delete --dry-run -- <absolute path>`, and remove `--dry-run` to run it. Items with `recycled` can be restored from the Finder Trash. For `ambiguous`, check the original path and the Trash, and do not resend the same deletion automatically.

To wait for a cooperative `flock` to be released, enqueue with `delete-queue -- <absolute path>` and check the final result with `delete-queue-status <job-id>`. Cancel with `delete-queue-cancel <job-id>` while it is `pending`.

### On Linux

Use the absolute paths of the executable and configuration in the [Linux CLI example](docs/linux.md#初回インストール). Check the targets with `delete --dry-run -- <absolute path>`, and remove `--dry-run` to run it. Items on the same mount as the home Trash can be moved. Items with `recycled` can be restored with a file manager that supports the freedesktop Trash. For `ambiguous`, check the original path and the Trash, and do not resend the same deletion automatically.

### On Windows

On Codex hosts that support formal sandbox permission requests, where the effective configuration requires and allows such a request, run actual deletions with the request from the first attempt. A dry-run does not guarantee permission to access the Recycle Bin. If Windows administrator rights are needed, the agent starts an administrator CMD within the permitted scope and runs and checks the result with the same installed CLI and configuration. If your UAC consent is needed, it guides you through the step. Prunlet itself never elevates automatically and does not retry denials or unknown results another way. See the [integration guide](docs/integration.md#sandboxとゴミ箱へのアクセス) for details.

```cmd
C:\Users\you\.local\Prunlet\bin\prunlet.exe --config C:\Users\you\.local\Prunlet\config.json delete --dry-run --paths-file C:\work\delete-paths.json
C:\Users\you\.local\Prunlet\bin\prunlet.exe --config C:\Users\you\.local\Prunlet\config.json delete --paths-file C:\work\delete-paths.json
```

Replace the executable and configuration with the absolute paths of your installation. In Codex, specify `cmd.exe` and `login: false`. Do not expand target paths with spaces, Unicode, many items or long paths in the shell; pass them as absolute paths in a UTF-8 JSON array. `--paths-file` accepts 1 to 1024 entries and up to 4 MiB on Windows (256 entries and 1 MiB on macOS and Linux); MCP `delete_files` and `delete-queue` accept up to 256 paths per request. Over-limit requests are refused as a whole without changing anything, so split the list.

```json
["C:\\work\\project\\unused.txt", "C:\\work\\project\\other.txt"]
```

Use a normal `delete` for empty folders and `delete --recursive --paths-file <absolute JSON path>` for folders with content. Simple paths can also be passed as `delete [--dry-run] [--recursive] -- <absolute path> [...]`. Wildcards, network paths and unknown reparse tags are not handled. For a link, the link itself is deleted and its target is not traversed. An ordinary file with the same name as a Windows reserved name, such as `NUL` or `NUL.txt`, is permanently deleted after its identity is checked, without further confirmation. It does not go to the Recycle Bin. Reserved-name ancestors, directories and links are not part of this exception. For ordinary names, permanent deletion is attempted after matching the original item and name only when Windows reports that the target is too large for the Recycle Bin, or when the Recycle Bin is unavailable and the target drive's immediate-delete setting has been confirmed.

The result has `dryRun`, `items` and `warnings`. Check each item's `path`, `kind`, `status` and optional `error`. The statuses are `recycled`, `permanently_deleted`, `would_recycle`, `would_permanently_delete`, `already_absent`, `failed` and `ambiguous`; no file operation ID, backupPath, hash or size is returned. `permanently_deleted` means the specified original name was deleted without moving it to the Recycle Bin; it does not mean other hard links or backups were erased. `failed` and `ambiguous` are not treated as success.

Restore `recycled` items from the Windows Recycle Bin. The original name of a `permanently_deleted` item cannot be restored from the Recycle Bin. Prunlet has no file restore command or MCP tool. If an item already exists at the Recycle Bin's restore location, check the conflict in the Windows UI and do not overwrite it.

If an item cannot be moved because it is in use, lacks permissions or hits path limits, check the result. On failure, `error` includes the target and the error code, and when in use, it also returns the PID, name and file path of the observed holders. In recursive permanent deletion, the result's `path` and the `Target` in `error` refer to the specified folder. A `Failure entry`, if present, gives the absolute path of the failing entry, and the holder diagnostics also refer to that entry. See the [integration guide](docs/integration.md#使用中のファイルと同時実行) for the scope and limits of the diagnostics. If the target name is replaced during Shell processing, a different item may be moved to the Recycle Bin. Prunlet checks the moved item and stops with `ambiguous` if it does not match. For `ambiguous`, check the original target and the Windows Recycle Bin; the same deletion is not resent automatically. For an ordinary file with a reserved name, a dry-run returns `would_permanently_delete` and does not actually delete it. Any other `would_recycle` is the result of pre-checking the input and cannot predict whether it will become `permanently_deleted` at run time or whether the actual move will succeed.

Access rights while in the Windows Recycle Bin, and permission inheritance from the parent of the restore location, also follow Windows behavior. Hard links share not only content but also ACLs, so permission changes made when moving to the Recycle Bin also apply to the surviving aliases.

### Deleting files in use after waiting

To wait for a target in use on Windows, enqueue it in the explicit `delete-queue` before starting the deletion. A normal `delete` still returns its result synchronously.

```cmd
C:\Users\you\.local\Prunlet\bin\prunlet.exe --config C:\Users\you\.local\Prunlet\config.json delete-queue --paths-file C:\work\delete-paths.json
C:\Users\you\.local\Prunlet\bin\prunlet.exe --config C:\Users\you\.local\Prunlet\config.json delete-queue-status <job-id>
C:\Users\you\.local\Prunlet\bin\prunlet.exe --config C:\Users\you\.local\Prunlet\config.json delete-queue-cancel <job-id>
```

Specify non-empty folders with `delete-queue --recursive --paths-file <absolute JSON path>` and simple paths with `delete-queue [--recursive] -- <absolute path> [...]`. The enqueue response does not mean the deletion is complete. Check the status and final result with the returned job ID. In MCP, give `action: "enqueue"`, `"status"` or `"cancel"` to the existing `delete_files`. See the [integration guide](docs/integration.md#明示的な削除待機キュー) for details.

Before deleting, the queue pins the identity of the target, its parent and, for recursive targets, its children, and waits without a time limit only for sharing and lock violations. If an identity changes while waiting, it is cancelled; failures or unknown results after the deletion has started are not resent. Up to 8 jobs per user and Windows session (including those retained after completion). A job can be cancelled only while waiting, and the final result is kept for one hour. Jobs live only in the memory of a dedicated temporary worker and are neither file operation records nor restore IDs. If the result cannot be confirmed because it expired or the OS or worker ended, check the original target and the Windows Recycle Bin, and do not resend the same deletion automatically.

## Registry deletion and restoration

Permitted local HKCU, HKLM and HKU keys or values can be backed up and deleted in an explicitly specified 32- or 64-bit view. Give the key path as an absolute path, and pass exactly one after `--`. Without `--value-name` the key is the target; with it, the literal value name is. The default value has an empty name, so use `--value-name=`, which PowerShell does not drop as an empty argument. Value deletion cannot be combined with `--recursive`. Deleting a key with subkeys requires `--recursive`.

A colon in a key name can be given as is. For example, the end of `HKCU:\Software\Example\C:#Program Files#Fixture.exe` is a single key name. Names containing `%5C` and the like are also taken literally, with no URL decoding.

```text
prunlet --config <absolute path> registry-delete --view 64 --dry-run -- HKCU:\Software\Example
prunlet --config <absolute path> registry-delete --view 64 --recursive -- HKCU:\Software\Example
prunlet --config <absolute path> registry-delete --view 32 --value-name= -- HKCU:\Software\Example
prunlet --config <absolute path> registry-restore <operation-id>
```

Backup data and records are protected with permissions that only the current user and SYSTEM can access, and records whose permissions have been tampered with are preserved without being restored or cleaned up. Saving key data and full access rights requires `SeSecurityPrivilege`. Where permissions are insufficient or transactions are unavailable, it stops before deleting and never elevates automatically. Restoring a value does not change the parent key's access rights. For protected targets in 64-bit Windows, a 64-bit process and view 64, `--access-mode backupRestore` can be given explicitly for each deletion, dry-run and restoration. It requires `SeBackupPrivilege` and `SeRestorePrivilege` in the current effective token, and does not gain access by changing ACLs or ownership. The default is `normal`, with no automatic switching. Also check the [selection conditions and limits](docs/integration.md#保護されたレジストリへの明示アクセス). See [DESIGN.md](DESIGN.md#レジストリの削除と復元) for the storage format and transaction design.

Restoration goes to the original view and never overwrites or merges existing keys or values (including an empty default value). If the rights to restore Owner or SACL are insufficient, it rolls back and preserves the backup. The root itself, HKCR/HKCC, remote or relative paths, arbitrary registry links, unknown schemas, metadata and restore records that cannot be verified are refused. The key class is saved too, but the last write time is not restored, and volatile keys are restored as non-volatile keys. An operation interrupted after commit but before its record was finalized is preserved as unknown, and automatic cleanup and restoration are refused.

Entries under the effective user's `Software\Classes` alias are handled after verifying the destination. Deletion and restoration require additional write permission on the alias, and the alias's last write time may change. A dry-run does not write. Classes itself and other links are not targets. See the [design](DESIGN.md#レジストリの削除と復元) for supported paths and safety conditions.

If 6801 occurs in a virtual view from MSIX, you can use an [explicit session on normal Windows](docs/integration.md#通常windowsのレジストリを明示して操作する). You start a time-limited session on the normal desktop and connect from the CLI or MCP with a dedicated configuration selected. There is no automatic switching from the virtual view or automatic elevation, and keys in the virtual view are not treated as the keys of the same name on normal Windows.

If the session's response is lost, keep the reported `operationId` and check the saved result with `prunlet --config <absolute path of the same configuration> registry-reconcile <operation-id>`. Do not resend the same deletion, and do not guess an unknown commit result from whether the key currently exists. A successful restore consumes the snapshot, so the same operation ID cannot be restored repeatedly.

A registry `--dry-run` also checks the connection to the transaction with the same target, permissions and recursion as the actual deletion, and fails if it cannot connect. It neither writes nor deletes data, and does not guarantee that a following actual deletion will succeed.

## Retention and automatic cleanup of recovery data

`retentionDays` (default 7 days) and `maxRecoveryBytes` (default 1 GiB) apply only to registry snapshots. Windows retains and cleans up the Windows Recycle Bin, and Prunlet does not include it in capacity, retention or purge.

If an old configuration has no capacity-migration marker, or one below 1, the latest installation updates `maxRecoveryBytes` to 1 GiB once. A capacity changed by the user after the migration is kept on later updates.

`operations` lists registry operation IDs, and `purge <registry-operation-id> [--dry-run | --apply]` and `maintain [--dry-run | --apply] [--audit-records]` are also registry-only. Without options they only inspect. Before deletion, and in explicit and scheduled maintenance, protected records are inspected and the retention conditions applied. Ambiguous records and snapshots that cannot be verified are preserved.

## Migrating old file recovery data

`migrate [--dry-run | --apply [--if-needed | --retry-legacy-discard]]` cleans up old file backup data and operation records, and moves old registry records into the dedicated namespace. **Restore compatibility for old files ends.** Old file areas whose ownership can be confirmed are sent to the Windows Recycle Bin as they are, without unpacking the format, checking content hashes, copying or bundling. Files already in the Recycle Bin stay under Windows management. No conversion of old data for restoration and no reference files for the original permissions are created.

The installer runs `migrate --apply --if-needed` after registration and after retiring the old backend. Central old areas that were already evaluated are not rescanned, and on update it also checks owned old data on drives connected later. Normal file deletion, listing and maintenance do not scan old operation directories. See [DESIGN.md](DESIGN.md#旧ファイル復元データの明示移行) for the ownership checks and rescanning design.

Registry preservation, full ACLs and non-overwriting restoration are kept. Areas with registry traces, areas whose ownership cannot be confirmed, and offline or insufficiently permitted areas are left with a warning, and an incomplete file cleanup alone does not stop normal registry operations.

An interrupted file cleanup or one with an unknown result is not resent automatically and stops at a fixed empty gate. Only after checking the original folder and the Windows Recycle Bin, re-evaluate explicitly with `migrate --apply --retry-legacy-discard`. The installer never specifies this acknowledgement automatically. If installation fails after the migration has started, the new executables, configuration and registrations are kept and it does not roll back to the old binary.

## MCP

`prunlet --config <absolute path> mcp` starts a local stdio server. Standard output is reserved for JSON-RPC. MCP protocol versions 2025-11-25, 2025-06-18 and 2024-11-05 are supported. Synchronous deletion with `delete_files` works on Windows, macOS and Linux; enqueue, status and cancel work on Windows and macOS. The other tools in the table are Windows-only.

| Tool | Arguments | Purpose |
| --- | --- | --- |
| `delete_files` | Synchronous: `paths`, optional `dryRun` and `recursive`. Enqueue: `action: "enqueue"` and `paths`, optional `recursive`. Status and cancel: `action: "status"` / `"cancel"` and `jobId` only | Synchronous deletion of files and folders, and enqueue, status and cancel. Enqueue does not support `dryRun` |
| `delete_registry` | `path` and `view` (`"32"`/`"64"`), optional `valueName`, `recursive`, `dryRun` and `accessMode` | Deletes a key or value after preserving it. An empty `valueName` is the default value. `accessMode` is `normal` or `backupRestore` |
| `restore_registry` | `operationId`, optional `accessMode` | Restores a registry operation without overwriting. Protected access is chosen explicitly at restore time too |
| `reconcile_registry` | `operationId` | Reads and checks the saved result after a disconnect. Does not resend deletion or restoration |
| `list_operations` | None | Lists registry operation IDs (whether they can be restored is verified at restore time) |

The server announces the purpose of the deletion tools in `instructions`. On Windows the CLI is normally used, and MCP can be used when, for example, the installed executable or configuration cannot be expressed safely in CMD. Registry `purge` is an explicit CLI operation.

## Integration with Codex

See the [integration guide](docs/integration.md) for shared MCP registration on Windows, inspection of deletion input and how to unregister. See each installation procedure for the MCP registration examples and hook startup arguments on macOS and Linux. [macOS installation](docs/macos.md) · [Linux installation](docs/linux.md)

The hook denies direct deletions it recognizes and returns the detected command and the shell interpretation as the reason. When the shell is unknown, the judgement is a candidate one and not a confirmed local deletion. If search strings or remote scripts are denied, check the [hook inspection scope](docs/integration.md#hookの検査範囲). The CLI the hook points to is for deleting targets on the permitted host OS. It does not replace deletions or input automatically. Codex's approvals and management policies stay in effect.

## When the storage location check stops

With MSIX apps, new folders in AppData may be redirected to the package's own LocalCache. Redirection of ordinary directories is resolved to the actual location, but if an ancestor link or the actual location and attributes cannot be verified, it stops. Check the path and attributes shown in the error and, without disabling the verification, place the executable, configuration and recovery data in a dedicated directory such as `%USERPROFILE%\.local\Prunlet` if needed. Using the Codex package's LocalCache as a permanent location for recovery data is not recommended.

## When registry transactions are unavailable

If transactions are unavailable for the target hive, for example with `ERROR_RM_NOT_ACTIVE` (6801), the deletion is not committed; the original data is preserved and it stops. Availability may differ by hive even on the same PC. Do not switch to non-transactional deletion or repair the OS without knowing the cause; check the error and the target hive and view.
